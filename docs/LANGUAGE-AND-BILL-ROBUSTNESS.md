# Device drafts, language and bill robustness — 31 October 2026

## What “Saved on Phone” meant

The former button opened the existing IndexedDB offline draft/outbox workspace. It was not a phone backup, not an automatic save of every open form, and not confirmation that the server had accepted stock or money changes. The old “All changes saved” label was misleading when a form was only in memory.

The button is now **Offline drafts**. Its status counts explicitly saved device drafts and queued/review operations separately; it reports loading/storage errors instead of claiming everything is saved. The workspace explains that clearing browser data or losing the device can lose unsynced drafts. It preserves existing pending/syncing/accepted/conflict behaviour, attachment durability and explicit queue/retry. Clicking a main destination closes the workspace rather than leaving navigation apparently stuck; open unsaved editors require confirmation before leaving.

## Clean language selection

The header has one English/Hindi selector on phone and desktop; More no longer duplicates it. English controls use one language rather than English/Hindi pairs. Hindi primary navigation, shop metrics, bill fields and core actions use a bounded curated dictionary. **Hindi is a preview**, not a claim of full, independently reviewed localisation: detailed guidance and some screens remain English. No unvalidated Kannada interface is advertised; existing Kannada speech/message choices remain separate, as before.

Language choice is stored in the existing user/store-scoped IndexedDB cache, with an expiry. Account/store cleanup removes it with private device data. There is no new local database, localStorage token, server schema, environment variable or third-party dependency. A failed preference save does not block the current visit. Changing language does not modify bill data, units, paise, identifiers, approval payloads or reminder-language shop settings.

No Sarvam call is made to translate navigation or an approval screen. This avoids requiring connectivity/credits for basic controls and avoids unpredictable wording of financial confirmations. Existing explicit reviewed Sarvam workflows remain available under their existing permissions/flags. A fluent reviewer and broader device/language matrix are still needed before removing the Hindi-preview label.

## Add new bill repairs

- New bill is disabled while a request is running, and main navigation cannot interrupt an active save. Read-only recovery navigation has its own loading state so this guard does not block opening a case. It clears stale receiving/item editors only when a new editor is deliberately opened.
- Starting another bill or returning to the saved list prompts before discarding unsaved purchase/receiving fields, photos or pasted text. Continue keeps the exact values. Main navigation and unload also guard unsaved work.
- Switching between Bills, Stock and Expiry keeps the current editor. Selecting a new language keeps its data.
- A successful device save establishes a saved local copy, so opening Offline drafts does not falsely treat that same copy as lost unsaved edits. Later changes need saving again. Device save remains provisional until sync acceptance.
- The editor scrolls into view when opened. Narrow phone forms stack fields; the header avoids squeezing the generic Workspace label beside the language selector. Duplicate More links were removed while all actual destinations remain reachable.

## Original sources and retry integrity

Manual typing after choosing a photo previously saved the JSON purchase fields without that photo. Manual typing after pasting text could similarly lose the original text. The existing endpoints now support explicit manual proposals and save the preserved source and typed fields together without invoking AI:

- `POST /api/purchases/document`: optional multipart `manual_draft`, strictly validated PurchaseDraft JSON (maximum 64,000 characters). Without it, the existing extraction path is unchanged. Invalid manual JSON/authority fields reject safely before a purchase is created.
- `POST /api/purchases/extract-text`: optional typed `manual_draft`. With it, the original text becomes a source attachment and provider extraction is skipped. Existing extraction clients remain compatible.
- Existing v1 `purchase_create` sync payload: optional `source_text` (1–18,000 characters). Original pasted text survives device save, reload and server sync; legacy payloads remain valid. Original document metadata/upload dependencies are unchanged.

File MIME/size validation, verified tenant context, CSRF, write permissions, duplicate supplier/reference checks and immutable approval rules still apply. These paths create **drafts**, never receipt/stock events or approved invoices. No AI-provider telemetry/spending is generated by manual capture.

For a manual photo request, the client encodes multipart bytes once, keeps the exact original Content-Type boundary and operation key, and reuses them on a retry. The server's existing transactional idempotency therefore returns its original response after a lost reply, rather than creating another purchase. These bytes are held only in the open editor; durable offline work continues through the existing IndexedDB outbox. Do not claim arbitrary unsaved editor state survives process/device loss.
